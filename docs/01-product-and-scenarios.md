# 产品范围与ERP演示场景

## 1. 产品定义

ERP Agent Copilot 面向需要跨库存、物流供应商和订单系统办理业务的企业用户。系统不是普通问答机器人，而是一个受状态机、权限策略、业务规则和审计约束的ERP Agent Runtime。

### 一句话价值

将自然语言ERP业务需求编译为可解释的Tool DAG，自动完成跨系统查询、决策和提交，并保证写操作经过审批、执行可恢复、结果可验证。

### 目标用户

- 业务人员：用自然语言查询库存、物流和订单状态。
- 订单运营人员：快速完成跨系统下单和订单状态维护。
- 平台管理员：管理Tool、Scope、知识库和租户策略。
- 评测与安全人员：执行回归测试并分析失败、越权和注入事件。

## 2. 产品目标

- 支持工具注册、检索、参数提取和结构化执行。
- 支持ERP业务知识RAG、来源引用和无依据拒答。
- 支持多步骤Plan DAG、并行只读步骤和串行写步骤。
- 支持RBAC、Tool Scope、风险分级和人工审批。
- 支持Checkpoint、重试、取消、超时和Worker重启恢复。
- 支持离线评测、Record/Replay、Trace和性能报告。

## 3. 非目标

- 不从零训练通用大模型。
- 不把有调用次数限制的真实ERP系统作为日常开发和评测依赖。
- 不创建多个可以自由对话、行为不可控的Agent角色。
- 不拆分十几个缺少独立扩缩容需求的微服务。
- 不在没有基线评测时进行Embedding或Reranker微调。
- 不把实时库存、价格、供应商和订单状态保存为向量知识库中的当前事实。

## 4. 场景A：库存、供应商与订单创建

### 用户请求

> 当前库存量充足的话，请帮我下一个发往上海的20KG苹果订单，并选择合适的物流供应商。

### 期望行为

1. 识别产品名称、数量、目的地和用户的下单意图。
2. 查询苹果库存，判断是否满足20KG需求。
3. 查询发往上海的物流供应商及配送时效、费用、评分和状态。
4. 根据业务规则筛选可用供应商，组装订单参数。
5. 在创建订单前进行Schema校验、权限检查和用户确认。
6. 调用订单创建Tool，返回订单号、供应商和关键结果。

### 验收标准

- 库存不足时不得创建订单，并说明缺口。
- 供应商候选必须来自Tool结果，不能由模型编造。
- 创建订单前展示产品、数量、目的地、供应商和费用摘要。
- 同一幂等键重复提交不能产生重复订单。

## 5. 场景B：业务写操作与审批

### 用户请求

> 将订单123的状态更新为“运输中”；如果缺少必要信息，先告诉我需要确认什么。

### 期望行为

1. 识别更新订单状态的写意图和订单ID。
2. 查询订单当前状态，检查目标状态转换是否合法。
3. Policy Engine识别更新操作为WRITE级操作。
4. Run进入`WAITING_APPROVAL`，展示订单、原状态、目标状态和影响。
5. 审批通过后使用幂等键执行更新。
6. 重新查询订单确认状态已更新。

### 验收标准

- 未审批时写Tool调用次数必须为0。
- 审批用户必须具备正确租户、Scope和审批权限。
- 重复提交、Worker重启和消息重投不能造成重复更新。
- 状态更新失败时保留可定位的错误，不自动改变用户未确认的字段。

## 6. 场景C：异常、安全与任务恢复

### 演示内容

- 用户输入要求跳过库存校验或泄露系统凭据。
- 外部ERP Tool URL尝试访问未授权地址。
- 库存查询、供应商查询或订单接口超时、限额或返回暂时性错误。
- Worker在部分Step完成后被终止。

### 验收标准

- 业务文档内容始终作为数据，不能覆盖系统策略和写操作审批。
- SSRF和出口访问策略在发出网络请求前拦截危险地址。
- Worker恢复后跳过已经成功的订单写Step。
- 瞬时错误在预算内退避重试，状态未知的订单写Step先对账。
- 所有拦截、恢复和降级行为写入安全事件或Run事件。

## 7. V5能力复用边界

| V5能力 | V6处理方式 |
|---|---|
| OpenAPI工具导入 | 保留业务思想，重写为OpenAPI 3.x校验、版本化和风险分级 |
| Milvus向量召回与Rerank | 保留两阶段思想，重写为可评测的混合检索接口 |
| 工具选择 | 保留训练数据和召回逻辑作为基线 |
| 参数提取与缺参补全 | 增加JSON Schema、来源追踪、冲突检测和用户确认 |
| MCP | 保留协议，重做持久连接、健康检查和错误契约 |
| Flask线程池任务 | 不复用，改为FastAPI、Celery、Redis和持久Run状态 |
| MongoDB Task状态 | 不复用，改为PostgreSQL事件和Checkpoint |
| 简单注入判断 | 作为历史基线，重做五层安全策略 |

## 8. 演示顺序

推荐10分钟演示顺序：

1. 1分钟说明人工跨系统下单痛点和V5局限。
2. 3分钟演示库存查询、供应商选择和订单创建。
3. 2分钟演示订单状态更新的审批暂停与确认。
4. 2分钟演示缺参、库存不足、注入或SSRF拦截。
5. 1分钟演示订单写操作超时后的对账恢复。
6. 1分钟展示评测报告和Trace。
